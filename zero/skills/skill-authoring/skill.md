# Skill Authoring（编写用户技能）

## 数据布局（Data layout）

- 用户技能根：**以 `## Skills` 段落里 `User skills live in ...` 的绝对路径为准**
  （默认 `~/.zero/skills`）。数据根可能被宿主改到别处，不要硬编码 `~/.zero`。
- 一个技能一个目录，入口固定为 `skill.md`：

      <用户技能根>/<name>/skill.md

  `<name>` 用小写 kebab-case，且与 frontmatter 的 `name` 保持一致。
- 支持文件放同一目录下：`references/*.md`、`scripts/*.py`、`assets/*`；
  正文用相对路径引用，运行期按 skill.md 所在目录解析。
- 同名时**用户技能覆盖包内技能**（按 frontmatter 的 `name` 判定，不是目录名），
  覆盖前先问用户。
- 包内技能（`<available_skills>` 中 `location` 落在应用包或源码树里的那些）
  只读，不要写；需要定制就新建同名用户技能覆盖。

## 使用时机（When to use）

- 用户说「加个技能」「把这个流程记下来」「以后遇到 X 就这样做」。
- 用户要求修改已有技能的触发条件、执行流程或输出格式。
- 同一套流程/偏好被反复使用，值得沉淀为可复用规则。
- **不要** 在以下情况使用：
  - 一次性任务——直接做完即可，不需要建技能；
  - 用户只是问某个技能在哪、怎么用——读对应 `skill.md` 回答；
  - 用户要改的是系统提示词、配置或业务代码，而不是技能内容。

## 创建流程（Workflow）

### 1. 对齐需求（先问，但别审问）

确认四件事：解决什么问题、什么时候触发、输出/交付形态、明确不适用的情况。
用户描述已经足够时直接动手，不要为了凑流程反复追问。
要沉淀的是**可复用规则**，不是这次任务的具体细节。

### 2. 查重与命名

1. 在 `<available_skills>` 中查同名技能；已存在时问用户是覆盖还是换名。
2. 名字表达职责（如 `api-doc-review`、`release-check`），不用 `my-skill` 这类空名。
3. 目录名与 frontmatter `name` 保持一致，避免覆盖判定与展示名错位。

### 3. 写 skill.md

frontmatter 只放 `name` 与 `description`：

- `description` 是**唯一的路由信号**——它进入系统提示词，正文只在命中后才加载。
  一段话写清：做什么、何时触发、覆盖哪些场景、关键词；不要写 Markdown 结构。
- 「何时触发」要写成未来的自己能判断的条件，而不是笼统的「用户需要时」。

正文是给模型读的操作说明，用**祈使句**，按需选章节：

| 章节 | 用途 |
|------|------|
| 数据布局 | 读写路径、状态文件、目录约定 |
| 使用时机 | 触发条件 / 不触发条件 |
| 执行流程 | 编号步骤，写清先后与判定 |
| 示例 | 1–3 个「用户说 → 怎么做」的具体例子 |
| 参考资源 | 支持文件清单：主题 / 使用时机 / 相对路径 |
| 注意事项 | 语言、格式、安全与边界约束 |

简单技能不必凑满模板；关键路径、命令与判定规则必须自包含在正文里，
不要把决定性信息只藏在外部链接或脚本注释里。

### 4. 需要脚本时

- 脚本放 `<技能目录>/scripts/`，调用时用**绝对路径**：
  `python <技能目录>/scripts/<name>.py ...`
  相对路径会按进程 cwd 解析，不要用。
- 在 skill.md 里写清子命令、参数、stdout 摘要与退出码约定；
  参数或状态非法时写 stderr 并以非 0 退出，不做静默失败。
- 脚本自行处理编码（强制 UTF-8 输出），不要把编码依赖挂在命令前缀上。
- 脚本运行受正常权限包络约束（可写范围、网络、审批），不要在技能里
  假设或要求额外权限。
- 有状态文件时写明「唯一写入口是脚本，不手工编辑」，并采用原子写。

### 5. 写入与自检

1. 用 write/edit 工具、绝对路径写 `<用户技能根>/<name>/skill.md`
   （用户技能根在默认写集合内，无需逐文件审批）。
2. 读回文件，确认 frontmatter 能解析、`name` / `description` 非空、
   正文没有把关键步骤写成含糊的「视情况而定」。
3. 有脚本或支持文件时，跑一次最小用例，确认相对路径与输出符合正文描述。
4. 新技能在**下一轮**的 `<available_skills>` 中出现（清单按目录/文件 mtime
   失效，无需重启）。没出现时检查路径是否为
   `<用户技能根>/<name>/skill.md`，以及 frontmatter 是否合法。

### 6. 汇报

告诉用户：技能名、`skill.md` 绝对路径、触发场景、如何验证（一句话即可）。
覆盖了内置技能时明确说明「同名覆盖，只影响用户目录」。

## 示例（Examples）

### 示例 1：把重复流程固化成技能

用户说：「以后我让你看 PR，都先跑测试再按安全/性能/可读性三段给建议，记下来。」

1. 确认触发词（「看 PR」「review 这个 MR」）、输出结构、不适用范围（纯咨询不跑测试）。
2. 查重：`<available_skills>` 里没有 `pr-review`。
3. 写 `<用户技能根>/pr-review/skill.md`：description 写清触发条件与关键词；
   正文按「使用时机 → 执行流程（跑测试 → 三段评审）→ 输出格式 → 注意事项」组织。
4. 读回自检，汇报路径与触发方式。
5. 不改任何内置技能，也不需要重启应用。

### 示例 2：调整已有用户技能

用户说：「刚才那个技能太啰嗦了，输出只要结论和风险。」

1. 读现有 `skill.md`，确认它来自用户目录（`location` 不在应用包内）。
2. 只改「执行流程 / 示例 / 注意事项」中与输出相关的部分，frontmatter 的触发条件保持有效。
3. 若用户要求改触发条件，同步更新 `description` 的关键词，避免路由漂移。
4. 读回自检后汇报改动点。

## 注意事项（Notes）

- **description 会进入系统提示词**：保持一到三句，不要把整篇正文塞进去。
- 不把一次性任务细节、密钥、个人信息、临时路径写进技能。
- 不堆砌无关关键词来「骗触发」；触发条件准确比关键词多更重要。
- 用户技能根之外的位置（应用包、系统目录）一律不写；确需写到别处时走权限流程。
- 修改技能无需重启；若用户同时改了配置，按配置流程提示重启。
